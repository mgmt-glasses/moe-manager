# ドキュメント運用

このドキュメントは、開発方針や仕様ドキュメントを増やす・更新するときのルールを定義します。

## 基本方針

- 新しい方針を追加する前に、既存ドキュメントに追記できないか確認する。
- 同じ内容を複数ファイルに重複して書かない。
- 詳細を書くファイルと、入口として案内するファイルを分ける。
- 方針変更はコード変更と同じく PR でレビューする。
- 実装ルールを変えた場合は、関連ドキュメントも同じ PR で更新する。

## ドキュメントの役割

| ファイル | 役割 |
| --- | --- |
| `README.md` | ドキュメント全体の入口 |
| `development-policy.md` | チーム開発の基本ルール |
| `architecture-guidelines.md` | 設計方針、依存方向、モジュール境界 |
| `implementation-guide.md` | 実装手順、配置場所、PR 前チェック |
| `mvp-summary.md` | MVP の目的、機能、画面の要約 |
| `api-guidelines.md` | API 共通仕様とドメイン方針 |
| `database-guidelines.md` | DB 設計とマイグレーション方針 |
| `documentation-guidelines.md` | ドキュメント更新ルール |

## 書き方

- 冒頭に、そのドキュメントの目的を書く。
- 判断基準を先に書き、詳細や例は後ろに置く。
- ルールと背景を混ぜすぎない。
- 変更されやすい具体例は、正とする詳細ドキュメントへリンクする。
- 古くなった内容を残す場合は、現行方針ではないことを明記する。

## 更新が必要なケース

以下の変更をした場合は、ドキュメント更新を検討します。

- モジュール構成を変更した。
- API の共通レスポンス形式を変更した。
- DB テーブル、カラム、マイグレーション方針を変更した。
- ブランチ運用、レビュー運用、PR ルールを変更した。
- 新しい外部サービス、LLM、TTS、DB を導入した。
- 実装手順や配置場所が変わった。

## 未確定事項の扱い

既存ドキュメント間で方針が揺れている場合は、関連する方針ファイルに以下を明記します。

- 現時点で正とする名称や方針
- 旧表記として扱う名称
- 詳細仕様の参照先
- 将来対応に回す内容

現在の整理済み項目:

- 娯楽時間 DB テーブル名は `screentime_records` を正とする（旧表記 `entertainment_records` / `entertainment_times` は使わない）。
- ボイス設定の domain/DB 名は `voice_preset_id` を正とし、API では `voiceId` として返す。変換は HTTP handler に閉じる。
- 統計は MVP では専用テーブルを持たず、都度計算を正とする（`detail/仕様書.md` 5.5節の統計テーブル記述は読み替え対象）。
- 「Phase」は文書により意味が違うため、`implementation-guide.md` ではモジュール対応と API 実装順を分けて扱う。
- MVP バックエンドの実装言語は Go とする。`detail/ARCHITECTURE.md` と `detail/Rule.md` の Python / FastAPI 構成は旧設計として扱う。

## 整理ルール

ドキュメントが増えてきたら、以下の順で整理します。

1. `README.md` に入口を追加する。
2. 既存ファイルと重複していないか確認する。
3. 重複している場合は、どちらか一方を正としてリンクに寄せる。
4. 古い内容は削除するか、移行先を明記する。
5. PR で「どのドキュメントを正とするか」を説明する。
